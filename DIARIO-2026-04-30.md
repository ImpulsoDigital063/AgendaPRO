### 7. Performance — 3s → ~700ms (5 fases de otimização)

Eduardo reportou que ao tocar no ícone, o app demorava ~3s pra abrir. Fiz auditoria técnica e implementei em camadas:

**Fase 2 — Splash + paralelizar (commit `48589b2`):**
- `manifest.ts`: `background_color: '#f9fafb'` (branco) → `'#030510'` (admin-bg-deep brand). Adicionei ícones com `purpose: 'maskable'` pro Android Adaptive Icons.
- Criei rota dinâmica `/splash` via **next/og** — gera PNG splash com fundo dark + monograma "PRO" gradient. 8 resoluções diferentes via media query (cobre iPhone SE até 15 Pro Max).

- Layout + page: `Promise.all` em todas queries paralelizáveis. Antes 9 round-trips sequenciais, agora 4.

**Fase 3 — Skeleton + SW + preconnect (commit `b5dabdb`):**
- `loading.tsx` no /admin com skeleton **instantâneo** (mesma silhueta do dashboard real).
- **Service Worker** manual em `/public/sw.js` — cache-first pra estáticos imutáveis (`_next/static/*`, ícones, logos, fontes), network-only pra HTML/API (sempre fresh). Sem dep externa.
- `RegisterSW.tsx` client component — registra com `setTimeout(0)` pra não competir com first paint.
- `<link rel="preconnect">` Supabase no `<head>` — economiza ~200ms TLS handshake na 1ª query.
- `<link rel="dns-prefetch">` MP — acelera abertura de checkout.

**Fase 4 — Cache cross-request + Suspense streaming (commit `79d2639`):**
- 5 funções com **`unstable_cache`** em `admin-data.ts` (TTL 15-60s) usando service-role client (bypassa RLS, mas todas filtram por `business_id` validado pelo layout):
  - `getAppointmentsToday` (15s)

  - `getRecentActivity` (60s)
  - `getPendingAppointmentsCount` (30s)
  - `getPendingClaimsCount` (30s)
- Page refatorada em sections async dentro de `<Suspense>`:
  - `KPIsSection` (com skeleton fallback)
  - `ClaimsLinkSection` (fallback null)
  - `TodaySection` (fallback null)
  - `UpcomingSection` (fallback null)
  - `ActivitySection` (fallback null)
- KPIs e Today compartilham `getAppointmentsToday` cacheado — 1 query só.
- Validado com `tsc --noEmit` + `next build` zero warnings.

**Fase 5 — AppSplash interno estilo Facebook (commit `ba8e480`):**
- `AppSplash.tsx` client component no admin layout. Logo "PRO" gradient azul-roxo aparece em fullscreen com pop-in animation, segura por 400ms, fade-out em 200ms (600ms total).

## Decisões tomadas hoje (registrar)

1. **Webhook MP usa `after()` do Next 16** — responde 200 imediato, processa em background. Padrão pra qualquer webhook de terceiro com timeout apertado.
2. **PWA install copy: "1 toque pra abrir — sem precisar lembrar o site"** — em vez de "Acesse como app direto do iPhone". Entrega o benefício, não a tecnologia.
3. **Splash via next/og** em vez de gerar PNGs manuais ou usar @serwist/next — sem dep externa, edge runtime, cacheável no Vercel.
4. **Service Worker manual** em `/public/sw.js` em vez de `@serwist/next` — controle total, sem dep nova, estratégia conservadora (cache-first só pra estáticos, network-only pra HTML/API).
5. **`unstable_cache` + service-role client** pra dados de dashboard — bypassa RLS mas filtra explícito por `business_id` (validado pelo layout). TTL curto (15-60s) limita janela de dados velhos.
6. **AppSplash só em PWA standalone + 1x por sessão** — em browser comum splash interno é estranho ("já tô no site"); navegação interna não precisa de splash repetido.
7. **Dismiss do InstallBanner expira em 30 dias** em vez de eterno — usuário tem nova chance de instalar depois.
